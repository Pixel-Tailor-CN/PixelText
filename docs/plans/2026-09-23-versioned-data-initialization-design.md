# 数据版本驱动的初始化与本地列表刷新设计

状态：用户已确认（2026-09-23）。实施步骤见[实施计划](2026-09-23-versioned-data-initialization-plan.md)。

## 1. 背景与代码依据

用户设备约有 7000+ 条 SMS/MMS，冷启动出现“正在同步数据”弹窗，下拉刷新耗时较长。当前代码存在以下路径：

- `PixelTextApp.startMirror()` 在进程启动及每个 Activity 恢复时调用 `schedule(forceReconcile = true)`，要求全量对账。
- `MessageMirrorSynchronizer.reconcile()` 扫描 SMS/MMS；扫描期间将集合 `complete` 置为 `false`。`MirrorDao.replaceStructure()` 对未变化消息仍存在写入操作。
- `ConversationCacheRepository.isCacheReady()` 使用当前 SMS/MMS 扫描完成状态判断缓存就绪，混淆“已经初始化”和“本轮扫描进行中”。
- `ConversationListViewModel` 据此显示首次同步弹窗，但在会话流首次发射时关闭，不能准确表示整个初始化是否完成。
- 下拉刷新经 `refreshIncremental()` 访问系统 Provider；缓存被判为未就绪时退回全量对账，并与后台同步竞争同一把锁。
- `PixelTextApp` 另有启动时验证码对账；`MirrorChangeObserver.start()` 注册时会主动写入增量唤醒。这些入口也必须治理，不能只修改一处 `forceReconcile`。
- `MessageRepositoryImpl.getAllConversations()` 在缓存未就绪时有启动观察与调度的副作用，必须从列表读取路径移除。
- 智能卡片目前由 `MessageParser` 按需解析，没有持久化卡片解析结果；验证码和 MMS 文本已有持久索引。

以上是代码路径证据，不是设备耗时剖析结果；具体性能改善需要真机验证。

## 2. 已确认需求

1. 引入独立数据版本：旧安装没有记录时视为 `0`，本次目标版本为 `1`；不使用 App versionCode、versionName 或 Room schema version 代替。
2. 启动时版本不匹配才发起数据升级；全量镜像和约定的解析、索引完成后才更新版本。
3. 版本一致时，冷启动和恢复前台均不主动触发同步。
4. 会话列表下拉刷新永远只读 App 数据库，任何情况下都不能触发同步。
5. 取消每日全量对账，并取消旧安装已经注册的每日周期任务。
6. 保留实时消息变更入库和必要的后处理，不因取消启动扫描而破坏收发、已读、删除等操作。
7. 升级涵盖骚扰识别、验证码索引和 MMS 文本索引。用户已明确智能卡片继续按需解析，不预解析、不增加卡片持久化缓存。

## 3. 目标与非目标

### 目标

- 将一次性数据升级与普通列表加载彻底分离。
- 持久记录升级进度，失败、权限不足、进程死亡均不能误报成功。
- 将升级、实时事件、显式修复的触发原因区分开，避免普通启动隐式扫描。
- 版本一致、没有真实消息事件时，启动和下拉不访问短信 Provider、不新建同步任务。

### 非目标

- 不优化所有列表 SQL，不将骚扰隔离列表重构为全新查询架构。
- 不持久化智能卡片结果，不改变解析规则语义。
- 不删除系统短信、不改变自动清理策略，不因初始化主动下载远端 MMS。
- 不改变备份恢复和用户明确执行的修复操作所必需的同步权限。
- 不新增单元测试、测试目录或测试依赖；遵循项目验证规范。

## 4. 方案比较与选择

| 方案                               | 优点                                     | 不足                                               |
|------------------------------------|------------------------------------------|----------------------------------------------------|
| 只保存一个初始化布尔值             | 改动少                                   | 无法表达后续数据升级、多阶段失败和续跑             |
| 在 UI/ViewModel 中顺序扫描并写版本 | 调用直观                                 | 页面退出影响执行，重复创建页面易重复工作，难以恢复 |
| 持久版本状态 + 唯一后台升级任务    | 与页面解耦，可恢复、可观测、便于后续升版 | 需要统一多个索引模块的完成契约                     |

采用第三种方案。复用现有镜像和解析能力，增加薄的升级协调层，不重写同步引擎。

## 5. 状态模型与持久化边界

### 5.1 版本和阶段

设计中的状态至少包含：

- `completedVersion`：已经完整完成的数据版本，缺省为 `0`。
- `targetVersion`：当前升级任务的目标版本。
- `phase`：`PENDING`、`MIRROR`、`MMS_TEXT`、`SPAM`、`VERIFICATION`、`COMPLETED`、`FAILED` 或 `WAITING_PERMISSION`。
- 可恢复的阶段完成记录、最近失败类别及更新时间；进度仅记录计数，不保存短信原文。

逻辑执行顺序为镜像 → MMS 文本 → 骚扰识别 → 验证码索引 → 提交版本。阶段记录必须区分“已调度”和“已完成”。

版本状态存放在 App 私有数据库，生命周期与镜像数据绑定，不作为可移植用户设置导出。Room 表结构版本仍独立维护。镜像重建或丢失时，相应初始化标记必须失效，不能出现“空库但版本仍为 1”。

### 5.2 比较语义

- `completedVersion == currentVersion`：不安排升级任务。
- `completedVersion < currentVersion`：创建或恢复目标版本的唯一升级任务。
- `completedVersion > currentVersion`：视为数据来自更高版本；不得清空或降级写入版本，提示兼容性问题，不自动重新导入。

正常升级采用单调递增整数。只有升级流程最终完成才原子更新 `completedVersion` 并标记 `COMPLETED`。同版本的普通同步状态变化不能撤销已完成版本。

## 6. 组件职责

### 数据升级状态仓库

只负责持久化版本、阶段和错误，向 UI 暴露状态。不得在读取状态或订阅 Flow 时顺便触发同步。

### 数据升级协调器与 Worker

- 在具备权限的生命周期入口检查版本，安排唯一 WorkManager 任务。
- Worker 执行前再次检查目标版本和完成状态，防止旧任务或重复调度重复升级。
- 复用现有同步互斥机制，按阶段执行并校验结果；不持有镜像锁等待整个索引流水线。
- 失败按类型退出或退避重试，已完成阶段可恢复；不将预算耗尽、未完成结果或仅成功入队视作成功。
- 新目标版本不能复用旧目标的阶段完成记录。

### 既有镜像与派生模块

提供可等待、结果明确的操作。现有后台启动函数、吞掉异常的循环和仅入队的接口，不能直接充当升级完成证据。

### 页面和列表仓库

只订阅 App 数据及升级状态。下拉刷新不调用升级协调器、系统消息 Provider 或同步调度器。

## 7. 升级流水线与成功条件

### 7.1 全量镜像

- 对 SMS、MMS 进行完整对账，保留既有分页、删除复查、dirty token 和崩溃续跑保护。
- 一个升级目标需要一轮可识别的完整对账；不能因旧版本曾扫描完成就跳过本次升级要求。
- SMS、MMS 及线程、地址源需要达到本阶段要求的完整状态。预算耗尽则持久续跑，不能重头无限扫描或提前进入成功提交。
- 新事件仍可持久排队，不要求在持续收短信时 dirty 数量永远为零才完成；升级完成针对已确认的扫描边界，之后的真实变更由事件流水线处理。

### 7.2 MMS 文本索引

- 为本阶段镜像中的 MMS 建立符合当前索引版本及内容指纹的文本索引，包含明确的不可用状态。
- 需要读取已在系统本地存在的附件时，依赖现有附件复制和解析链路；不发起运营商网络下载。
- 待下载 MMS 可以保留“等待下载”记录，不阻塞整个数据升级。损坏、源已不可读等不可恢复内容必须有可解释的状态，不能伪装成解析成功。
- 临时 I/O、数据库错误等可恢复失败保留阶段待完成，不能仅因 indexer 已启动就提交版本。
- 提取可等待的批处理能力供升级使用；原有后台增量索引仍负责后续真实内容变化。

### 7.3 骚扰识别

- 沿用既有识别对象范围、开关、白名单及人工判定优先级，不扩大到现有分类器不支持的内容。
- 本次升级重新处理适用的自动识别结果，不能仅依靠 `getIdentifiedMessageIds()` 跳过全部旧数据。
- 用户关闭骚扰识别时不偷偷启用，记录本阶段按设置跳过；之后开启时沿用明确的功能启用处理流程。
- 分类失败不能当作完成；不存在有效模型等错误需要明确呈现，不能把失败分数当正常结果。

### 7.4 验证码索引

- 执行完整重建，沿用现有 generation 切换和失败清理，保留旧可用索引直到新索引成功激活。
- 去掉进程启动时无条件的 `scheduleReconcile()`；升级期间由协调器等待实际重建成功。
- 实时消息、规则更新等明确事件所需的索引更新继续保留。

### 7.5 最终提交

只有本目标的所有必要阶段成功，或按明确产品状态合法跳过，才提交新版本。界面收到会话列表、Worker 已入队、附件仍在等待执行都不是整体完成证据。

## 8. 启动、事件与调度边界

| 触发源                                             | 行为                                                                  |
|----------------------------------------------------|-----------------------------------------------------------------------|
| 首次启动或数据版本升级                             | 检查权限和版本，安排唯一升级任务                                      |
| 同版本冷启动、Activity 恢复                        | 注册必要的观察者、读取本地状态，不主动 markWake、markDirty 或调度同步 |
| 下拉刷新                                           | 只重新加载 App 数据库，任何状态均不触发同步                           |
| 系统真实 ContentObserver 事件、接收/发送/已读/删除 | 保留事件驱动更新和必要对账                                            |
| 每日定时器                                         | 取消，不再注册                                                        |
| 用户明确修复、备份恢复                             | 保留必要同步，不由下拉代替                                            |
| 规则或模型明确更新                                 | 保留对应派生索引更新，不通过普通启动隐式全量重建                      |

`MirrorChangeObserver.start()` 必须做到注册观察不等于同步，不能通过注册时人工生成 wake 绕过版本判断。`ConversationCacheRepository.startObserving()` 同样不能让列表读取间接调度同步。

旧周期任务名 `message-mirror-reconcile` 必须取消。对于升级前已排队的一次性任务，需要按原因清理或拦截旧的生命周期唤醒；保留已持久化真实事件和恢复任务，不粗暴清空全部 WorkManager 工作或 dirty 数据。

“启动不触发同步”不等于终止已有合法任务：之前中断的升级、真实收信或用户修复任务仍可恢复，日志需要能区分来源。

## 9. 下拉刷新与 UI

- 列表读取 API 为纯本地读取，移除“未就绪就启动观察/同步”的副作用。
- 下拉等待本次本地查询与列表加工完成即可收起指示器，不等待镜像锁、附件或解析任务。
- 空库显示空列表；初始化未完成时另外展示升级状态；数据库错误显示读取错误。以上分支都不能回退为系统同步。
- 升级进度来自升级状态仓库，不能再用 SMS/MMS 当前 `complete` 判断首次初始化，也不能在列表首次发射后提前隐藏升级状态。
- 建议复用现有进度对话框展示具体阶段，失败时显示错误与独立重试入口，不显示无限旋转的不可恢复状态；最终交互随本文一起评审。
- 已初始化的普通后台事件不弹出“首次启动需要同步”对话框。
- 本次不承诺下拉固定毫秒数：骚扰隔离的全量本地加工等既有成本仍可能存在，但不应再等待系统同步。

## 10. 失败、并发与特殊场景

- **无短信权限**：版本保持旧值，等待授权；授权后的版本检查可启动未完成升级。
- **退出页面或杀进程**：不写成功版本；由持久任务和阶段记录恢复，同目标任务去重。
- **阶段失败**：保持旧完成版本及错误原因，重试未完成阶段，不清空旧镜像和可用索引。
- **升级中收到新短信**：实时事件继续入队并保留 token，阶段结果提交不得覆盖更新或确认新事件为已处理。
- **备份恢复**：不恢复其他设备的初始化版本；既有恢复后重建继续保留。若与升级并发，需要串行协调相关写入，不能将升级前阶段记录套用到恢复后的数据。
- **规则变更**：派生阶段须识别其输入规则版本；执行中规则改变不得把旧规则结果登记为新规则完成，沿用模块版本/代次保护并补跑受影响阶段。
- **关闭功能**：遵循现有设置；合法跳过有明确记录，不能以关闭功能为由篡改其他阶段状态。
- **同版本反复启动或下拉**：只读状态和列表，不产生初始化扫描或首次同步弹窗。

## 11. 一致性代价与已知边界

取消启动和每日对账后，进程不在时其他应用修改旧消息、且没有可靠事件补偿的场景，可能暂时无法自动发现。不能为了弥补这一点偷偷在冷启动或下拉扫描。

因此保留明确的手动修复入口；普通实时事件仍可执行必要对账。若以后需要更强的离线变更发现能力，应另行设计并取得授权，不扩大本次范围。

## 12. 验收条件

1. 旧安装无版本记录：识别为 0，启动一次目标 1 的全量流水线；旧库仍可读。
2. 全新安装空库：权限齐全后完成初始化并写入 1；空 SMS/MMS 集合也可正确完成。
3. 各阶段完成前杀进程、失败或撤销权限：版本不能提前变为 1，恢复后不丢进度或数据。
4. 成功后连续冷启动和恢复前台：无启动触发的 Provider 扫描、验证码全量对账或首次同步弹窗。
5. 成功、空库、升级中和升级失败四种状态下拉：均仅查询 App 数据库，不调用同步或升级调度。
6. 目标由 1 升为 2：能够执行新一轮升级；来自更高版本的数据不会被自动降级。
7. 旧每日任务已取消，新安装不注册每日对账。
8. 新短信、MMS、本应用发送、标记已读及删除仍正确反映到本地列表；明确修复和备份恢复不失效。
9. MMS 待下载、不可用附件、临时解析失败能正确区分，不无限阻塞，也不误报全部可读。
10. 骚扰识别关闭、白名单和人工判定得到保留；验证码重建失败仍保留旧有效代次。
11. 在约 7000+ 条脱敏或合成数据上记录冷启动及下拉耗时、任务触发原因和各阶段计数，不记录短信原文。

实施后的验证使用 `./gradlew.bat :app:compileDebugKotlin` 和 `./gradlew.bat :app:lintDebug`，并进行上述相关真机验证。不新增或运行单元测试。没有设备时明确列出未验证项，编译通过不能代替系统行为验证。
