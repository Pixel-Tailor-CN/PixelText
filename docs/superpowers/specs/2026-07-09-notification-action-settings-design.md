# 通知快捷操作配置设计

## 背景

当前新短信通知固定显示 `已阅`、`回复` 两个操作；当短信被解析为验证码时，会额外插入一个 `复制验证码` 操作。现有实现可以满足基本需求，但操作顺序和文案都是硬编码，不同用户对通知操作的优先级偏好不同：

- 有些用户希望验证码复制放在第一个位置，减少点击成本。
- 有些用户希望保持 `已阅` 或 `回复` 在最前面。
- 有些用户希望缩短按钮文案，以适配自己的阅读习惯。

本次设计目标是在设置页新增一个独立的二级配置页面，让用户可以自定义这三个通知操作的顺序和文案，并确保普通短信与验证码短信都能按统一规则落地。

## 目标

- 在设置页新增 `通知快捷操作` 入口。
- 提供独立配置页，支持自定义以下 3 个固定 action：
  - `mark_read`
  - `copy_code`
  - `reply`
- 支持拖拽调整顺序。
- 支持编辑按钮文案。
- 提供一个验证码通知预览，实时反映当前草稿状态。
- 使用手动保存模式，未保存离开时弹出提示。

## 非目标

- 不新增动态 action 类型。
- 不改造 `NotificationActionReceiver` 的业务行为，只调整通知按钮的展示顺序和文案。
- 不引入第三方拖拽依赖。
- 不新增单元测试；按照项目约束使用编译和手动检查验证。

## 配置模型

通知快捷操作配置定义为固定三项，每项包含：

- `type`：操作类型
- `labelTemplate`：按钮文案模板
- `order`：排序序号

### 操作类型

- `mark_read`：已阅
- `copy_code`：验证码复制
- `reply`：回复

### 默认值

- `mark_read`：`已阅`，`order = 0`
- `copy_code`：`复制 {code}`，`order = 1`
- `reply`：`回复`，`order = 2`

### 占位符规则

只有 `copy_code` 支持占位符 `{code}`：

- 可以不包含 `{code}`
- 如果包含，最多出现一次
- 实际通知渲染时用验证码文本替换
- 预览页面使用固定示例码 `123456`

## 文案校验规则

所有按钮文案都在保存前校验，校验失败时不允许保存。

### 通用规则

- 去除首尾空白后不能为空
- 长度采用加权计数：
  - 英文或 ASCII 字符计 1
  - 中文或其他非 ASCII 字符计 2
- 最大长度为 8 个英文宽度，即：
  - 最多 4 个中文
  - 或最多 8 个英文
  - 中文英文混合按加权累计

### `copy_code` 额外规则

- `{code}` 最多出现一次
- 长度限制只计算固定文案部分，不计算 `{code}`
- 允许仅使用 `{code}` 作为完整文案

### 非 `copy_code` 规则

- 不允许使用 `{code}` 占位符

## 设置页入口

在 `SettingsScreen` 的“应用功能”分组中新增一个 `通知快捷操作` 设置项：

- 标题：`通知快捷操作`
- 摘要：展示当前排序后的文案摘要，例如 `已阅 · 复制 {code} · 回复`
- 点击后进入新的二级页面

## 配置页交互

### 整体结构

配置页使用单独 route，结构与现有 `SwipeActionSettingsScreen` 保持一致：

- 顶部栏左侧返回按钮
- 顶部栏右侧 `保存`
- 页面主体为滚动内容

### 内容区域

页面内容按以下顺序组织：

1. 说明卡片
2. 模拟通知预览
3. 可拖拽的 action 配置列表

### 预览

预览固定展示一条验证码短信模拟通知，用于同时展示 3 个 action：

- 发件人：示例服务名
- 内容：示例验证码短信
- action 文案和顺序实时取自当前草稿
- `copy_code` 使用 `123456` 替换 `{code}`

普通短信不单独绘制第二个预览，而是在说明文案中明确：

- 普通短信会自动隐藏复制按钮
- 其余按钮保持当前配置中的相对顺序

### 文案编辑

每个 action 项都包含：

- 操作名称
- 简短说明
- 单行文案输入框
- 拖拽手柄

输入框默认不请求焦点，只有用户主动点击后才进入编辑。

### 排序交互

- 每个 action 项右侧显示拖拽图标按钮
- 仅支持按住拖拽手柄后上下移动排序
- 拖拽过程中当前项浮起，其余项随顺序变化重排

### 保存模式

- 页面内部维护草稿，不实时写入设置
- 点击右上角 `保存` 后：
  - 对全部项执行校验
  - 校验通过则一次性写入设置
  - 保存成功后返回上一页

### 离开拦截

当草稿和已保存配置不一致时：

- 点击系统返回
- 点击顶部返回按钮

都弹出一个三选项提示：

- `放弃更改`
- `继续编辑`
- `保存`

若当前草稿存在校验错误，则对话框中的 `保存` 按钮禁用。

## 通知渲染规则

`SmsNotificationHelper` 改为按配置顺序构建可见 action：

### 普通短信

可用 action：

- `mark_read`
- `reply`

渲染顺序取自全局配置，但只保留这两个 action，保持相对顺序。

### 验证码短信

可用 action：

- `mark_read`
- `copy_code`
- `reply`

全部参与排序。

### 锁屏隐藏验证码

当命中锁屏隐藏验证码逻辑时：

- 公开版本通知不显示 `copy_code`
- `mark_read` 和 `reply` 仍按当前配置的相对顺序显示

## 持久化方案

继续沿用现有 `SharedPreferences` 配置仓库，不引入新的存储层：

- 为 3 个 action 分别存储文案模板
- 为 3 个 action 分别存储顺序值
- `AppSettingsRepository` 提供批量读取和批量保存接口
- `AppSettings` 暴露标准化后的 action 配置列表

读取时做标准化处理：

- 缺失项回退到默认值
- 空文案回退到默认值
- 排序冲突按默认顺序兜底并重新编号

## 代码结构

- `ui/screen/NotificationActionSettingsScreen.kt`
  - 新的配置页面与拖拽交互

### 需要修改

- `domain/settings/AppSettingsRepository.kt`
  - 暴露通知快捷操作配置

  - 提供保存接口

  - 增加入口与摘要展示
- `ui/AppNavigation.kt`
  - 增加 route
- `notification/SmsNotificationHelper.kt`
  - 使用配置驱动 action 标签和排序

## 验证方案

按项目约束，不新增单元测试。验证方式如下：

- 运行 `./gradlew :app:compileDebugKotlin`
- 手动检查新页面的以下行为：
  - 默认值展示正确
  - 文案编辑不自动获取焦点
  - 空文案和超长文案阻止保存
  - `{code}` 校验规则正确
  - 长按拖拽可以调整顺序
  - 未保存返回会弹出三选项提示
- 代码级手动检查通知构建逻辑：
  - 普通短信只显示已阅和回复，顺序按配置补位
  - 验证码短信按三项完整排序
  - 锁屏隐藏验证码时复制按钮不进入公开版本通知
